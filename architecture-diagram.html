Four Trust Zones

Each boundary is crossed by exactly one token. The two token types never mix.

Trust Zone 1 · Host Next.js (mock portal)
Momentum Life Insurance Portal (Host Application)
The insurer's portal where the user is already authenticated. It owns the session, knows the user's identity, role, and policy context, and issues a short-lived (15 min) RS256-signed handoff token, publishing its public key at /.well-known/jwks.json.

Trust Zone 2 · Embedded Child Next.js + TypeScript · own origin
Embedded AI Companion (Thuso)
The chat widget, loaded as pill and panel iframes from its own origin by a small host-side loader that renders no UI and never touches the token. It does NOT run its own login: identity arrives via postMessage, validated against a strict origin allowlist, and is forwarded to the backend on every request.

Trust Zone 3 · Companion Backend Node.js · Express + TypeScript
Companion Backend (backend-for-frontend)
A standalone service. It validates identity against the host's JWKS, enforces role-based access on every request, owns conversation memory, runs retrieval, orchestrates the two-step classify-then-act flow, and holds the gateway machine credentials as server-only environment variables.

Auth Middleware

  • Check iss / aud / exp
  • Role + deceased_flag gate access
  • Refuse and audit outside role

Session Memory

  • Postgres, per user + role
  • Rolling window + workflow-state card

Orchestrator

  • Escalation routing + audit logging
The user identity token and the gateway machine credentials are separate. Gateway credentials live only in the backend's environment and are never exposed to the browser; no frontend code path can reach them.

Request Lifecycle: Chat Message

End-to-end path of a single user message. At most two model calls, neither with any authority.

1

Frontend

POST /api/chat/message with Authorization: Bearer <jwt> and body { message, session_id }

2

Auth Middleware

Validates the JWT (RS256 via host JWKS, iss, aud, exp) and derives effective access from role + deceased_flag. Rejects with 401 and audits if invalid.

3

Session Manager

Loads the rolling window + workflow-state card for this user + role, appends the new message.

4

Model Call 1 of 2: Classify

Names the intent only (qa / whatif / update / claim). Untrusted output, validated in code with one re-prompt and a keyword fallback. Carries no authority.

5

Role Gate (our code)

Capability matrix check between the two calls. Refused: fixed empathetic template + audit entry, no second call, return.

6

Backend Action

Q&A: embed query, pgvector cosine over child chunks, swap in parent sections (below threshold: decline, no model call). Or: What-If formula, update validation, claims state machine.

7

Model Call 2 of 2: Compose

Phrases the result our code produced: grounded prompt of parent sections + trimmed history + state card. haiku, temp 0.3.

8

Persist + Return

Saves the turn and workflow state with the audit entry in one transaction. Responds with reply + session_id + role.

Document Ingestion Pipeline (RAG)

Offline pre-processing that grounds every answer in the provided policy documents.

Policy PDFs

Provided product documents

→

Chunking

Parents: guide sections · children: a few hundred tokens

→

Embedding

Children only · gateway titan-embed-v2

→

pgvector

Postgres · cosine (HNSW at scale)

Why pgvector: the gateway documentation's own showcase path, and Postgres is already our datastore, so it costs nothing extra to adopt: similarity search runs beside the profiles, sessions and audit tables, parent text is stored next to child embeddings, and a built-in index (HNSW) takes over when the full guide arrives at finals. The pipeline runs once, offline, as a standalone script; the backend never waits for it.

Two Independent Authentication Flows

The core security principle: these tokens never cross boundaries.

Flow 1

End-User Identity

Mock OIDC, modelled on real IdPs
Host app: OIDC login

user signs in at the portal

Host signs RS256 JWT

sub · role · policy_id · deceased_flag · iss · aud · exp

Short-lived token (15 min)

handed to the companion · renewed silently while the portal session lives

Backend validates via host JWKS

on every request · verifies but can never forge

Flow 2

Gateway Machine Auth

Provided · machine-to-machine
Backend: OAuth2 client-credentials

client_id + client_secret, backend env only

Token endpoint issues access_token

identifies the application, not the user

Machine token

used to call the AI Gateway

Gateway authorizes the app

never sees the end user

The user JWT never reaches the gateway. The gateway credentials never reach the browser. These are enforced as separate, isolated trust boundaries.
