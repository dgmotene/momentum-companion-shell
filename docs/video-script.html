Script (≈ 110 words)

Life insurance is one of the most important products people buy, and one they understand the least. Documents run to hundreds of pages, and the moment someone actually needs support — updating cover, filing a claim — is often the moment they're least able to read a policy guide.

We're building Lumina, an accessible AI companion that lives inside Momentum's client portal. It helps policyholders understand their cover in plain language, explore what-if scenarios, update their details conversationally, and guides bereaved beneficiaries through claims with care.

Our design has one non-negotiable: the assistant is trustworthy — grounded in Momentum's own documents, honest when it doesn't know, and respectful of who's asking.

Script (≈ 125 words)

The architecture has four clear trust zones. The host portal owns the authenticated session and signs a short-lived identity token with an RS256 private key. The companion lives in an iframe on its own origin — the browser isolates it from the portal at the DOM level; the token arrives via postMessage with a strict origin allowlist.

The companion backend is a Node.js backend-for-frontend. It verifies the token using the portal's public JWKS endpoint, runs retrieval against Postgres with pgvector, and holds the gateway credentials as server-only secrets. One Postgres instance holds the vector store, sessions, and the audit log — one system, one seed file, atomic writes.

The AI gateway sits outside. It never sees the user token; the browser never sees the gateway credentials. Every choice is justified in our architecture-decisions record.

Script (≈ 120 words)

Access control is where a lot of AI products get lazy. Ours doesn't.

This is Thabo, a policyholder — he sees the full portal: What-If, updates, claims, everything.

Now watch what happens when the linked policyholder profile carries a deceased-state flag. Anika, the beneficiary, receives a token — signed by the portal with RS256, verified by the backend via a public JWKS endpoint. Our backend can verify but cannot forge; the security boundary is honest.

The amber chip here isn't a UI trick. It reflects a token claim, and the backend re-checks it on every request — actually between the classify and reply model calls, so a refused action never generates an answer at all. Presentation and authorization stay in sync, but the authorization is the one that's binding.

Script (≈ 120 words)

Trust needs proof. Every answer Lumina gives cites the policy section it came from — this one, for example: "Per the Policy Guide, Cooling-off section, page 4." When someone asks something the documents don't cover, Lumina says so — the exact line from Appendix A: "I can't confirm that from the provided documents. I can explain what is available or refer this for human review." No invented facts. No confident guesses.

Claims is where empathy really matters. Anika lost her husband. Lumina opens with acknowledgement, not a form. Documents come in any order. Some are already on file from the death notification — she won't be asked to explain her loss twice. The 3-business-day SLA is visible, and a human is always one tap away.

Script (≈ 90 words)

We chose a middle path. Simpler than we could have: no microservices, no agent framework. More robust than a toy: real vector search, real session store. Every component maps to a specific requirement.

At finals, day one we wire live retrieval end-to-end — the full policy guide into pgvector, and the chat endpoint reading from it. Then we move card selection from the client into the model's structured output, so the same code path renders every rich answer. After that: real identity provider, audit persistence, and streaming responses.

Thank you.

Recording guidance

Pacing & delivery

  • Speak roughly 20% slower than feels natural. On playback it will sound just right.
  • Pause briefly before switching screens — gives the viewer's eye time to catch up.
  • Don't read verbatim from the script. Learn the beats, speak the substance.
  • If any speaker runs over 50 seconds in rehearsal, cut a sentence — don't rush.

Common mistakes to avoid

  • Reading the architecture diagram word-for-word. Point at zones and narrate the story — trust boundaries, tokens crossing.
  • Selling features instead of trade-offs. Judges care about why far more than what.
  • Ending flat. Speaker 5's last two sentences should carry the presentation home.
  • Typing on camera. The demo prompts are already baked into the wireframe. Just click.
